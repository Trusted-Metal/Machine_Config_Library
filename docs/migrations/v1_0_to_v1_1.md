## Change categories

The five categories from `docs/migrations/mock_v1_0_to_v1_1.md` / `docs/contributing.md`,
plus two new categories this manifest introduces:

| Category | Definition |
|---|---|
| Addition | New HDF5 attr/group with no equivalent in the previous version |
| Removal | Existing attr/group dropped; value is lost during forward migration |
| Name | Same group, different attr key; value preserved |
| Path | Same attr key, different HDF5 group; value preserved |
| Name+Path | Both group and key change; value preserved |
| **Consolidate** *(new)* | **N** per-instance attributes (one per optical train) collapse into **one** shared attribute. Lossless only if every source value already agrees; **disagreement is a hard error**, not a silent pick — see Change 1 below. |
| **Transform** *(new)* | An attribute's value is **parsed/restructured**, not merely relocated — new shape, explicit derivation rule required, not a straight copy. See Change 3 below. |

Both new categories should fold into `docs/contributing.md`'s table once this manifest is approved.

## Change 1: ClearBox relocated to `/Extensions/ClearBox/<train_id>/`

**Motivation:** every ClearBox instance currently duplicates `Output_Path` and
`Software_Trigger_Delay` — in practice both are the same value on every train
in a file (confirmed against `fixtures/reference_config_opcua_synchronous_sensors.h5`:
`Output_Path` = `/recordings/` and `Software_Trigger_Delay` = `3000` on both
trains), and each is only ever meaningfully read once by the ingesting
software. v1.1 stores both once instead of once-per-train. This is also an
opportunity to drop several attributes that have fallen out of real use
(`Video_Output`, `Correction_Grid_Domain_Shape`, `Inverse_Grid_Domain_Shape`,
`Custom_Video_Format`) and add one that's newly needed (`Firmware_Version`).
ClearBox itself moves out from under each train's `Optional_Components` into
a new top-level `Extensions` group, keyed by `train_id` so a file where only
*some* trains have a ClearBox stays faithfully representable.

### Before / after

```
v1.0:
/Machine/Optical_Trains/<train_id>/Optional_Components/ClearBox/
    <17 scalar attrs, incl. Output_Path, Software_Trigger_Delay>
    Correction_Data (dataset)
    Inverse_Correction_Data (dataset)
    Synchronous_Sensors/ (group, if present)
  — repeated per train, Output_Path and Software_Trigger_Delay always
    identical across trains today

v1.1:
/Machine/Optical_Trains/<train_id>/        ← Optional_Components ITSELF is gone, not just
                                              emptied — ClearBox was its only occupant
/Extensions/ClearBox/                      ← present only if ≥1 train has a ClearBox
    Output_Path                            ← ONE shared value (Consolidate)
    Software_Trigger_Delay                 ← ONE shared value (Consolidate)
    <train_id>/                            ← one subgroup per train that HAS a clearbox,
        <9 scalar attrs, incl. Firmware_Version>  keyed by that train's own train_id, not position
        Power_Characterization/            (Change 3)
        Correction_Data (dataset)
        Inverse_Correction_Data (dataset)
        Synchronous_Sensors/ (group, if present)
```

**`Optional_Components` is removed entirely on migration, not left behind
empty.** It existed on disk solely as a container for `ClearBox` — with
`ClearBox` relocated to `/Extensions/ClearBox/<train_id>/`, nothing remains
to hold there. This is still HDF5-layout-only for everything except
`Firmware_Version`: the StableModel's `OpticalTrain.optional_components.clearbox`
field is otherwise unaffected — the v1.1 adapter populates it from
`/Extensions/ClearBox/<train_id>/` the same as before, it just no longer has
an on-disk group of the same name to read it from directly.

`/Extensions` itself is present only if `ClearBox` and/or `TM_OPCUA` (Change 2)
exists — never an empty placeholder group.

### Consolidate conflict rule (rows 1, 16) — confirmed

- **Read (v1.1 file → StableModel):** unambiguous. One value exists on disk
  for each; every train's `clearbox.output_path`/`clearbox.software_trigger_delay`
  is populated with that same value.
- **Write (StableModel → v1.1 file), including v1.0→v1.1 migration:** collect
  the value from every train that has a `ClearBox`. If they don't all agree,
  **fail with a hard error** naming the conflicting trains and values —
  do not pick one silently, do not warn-and-continue.
- **Error name/message — resolved (2026-08-31).** Each language follows its own
  existing validation-error convention rather than a new shared exception type
  (mirrors the manifest's own precedent — `MachineConfigError::UnitMismatch` in
  Rust). Message content is standardized across languages so tests can assert
  on the same substrings regardless of the underlying type:
  `"Consolidate conflict on '<Output_Path|Software_Trigger_Delay>': trains
  disagree — <train_id>=<value>, <train_id>=<value>, ..."`
  - **Rust:** new `MachineConfigError::ConsolidateConflict { field: &'static str,
    detail: String }` variant (`rust/src/error.rs`) — struct-style, matching
    `UnitMismatch`'s multi-field shape.
  - **Python:** plain `raise ValueError(f"Consolidate conflict on '{field}': "
    f"trains disagree — {detail}")` — no new exception class, matching
    `v1_0/hdf5.py:230,248`'s existing convention.
  - **Node.js:** plain `throw new Error(...)`, same message, matching
    `v1_0/hdf5.ts`'s existing inline-throw convention — no new error class.
  - **Go:** plain `fmt.Errorf("consolidate conflict on %q: trains disagree — %s",
    field, detail)`, matching `capabilities/v1_0/hdf5/*.go`'s existing
    convention (lowercase start, per Go idiom) — no new error type.
  - **C++:** plain `throw std::runtime_error("Consolidate conflict on '" +
    field + "': trains disagree — " + detail)`, matching
    `v1_0/hdf5.hpp`'s existing Rule-8 validation throws — no new exception
    class.

  *(Correction, 2026-09-01: this bullet originally showed Go's and C++'s
  detail wrapped in parentheses — `"trains disagree (...)"` — inconsistent
  with the standardized em-dash template stated just above and with the
  actual Rust/Python implementations. C++'s implementation caught and
  corrected this itself by following the stated standard over this specific
  bullet; Go's initial implementation followed this bullet literally,
  producing a real cross-language inconsistency, caught in review and fixed
  in both this manifest and Go's code. All 5 languages now use the em-dash
  form.)*
- Scope: this only applies on the v1.1 write/migration path. Reading a v1.0
  file under the v1.0 adapter is completely unaffected.

## Change 3: `Volts_To_Watts_*` replaced by `Power_Characterization/`

**Motivation:** today's `Volts_To_Watts_Algorithm`/`Volts_To_Watts_Params` pair
stores only the *derived* fit (an algorithm name and a positional,
algorithm-dependent CSV string) — never the raw voltage/wattage measurements
used to derive it, and the params string has no self-describing structure.
`Power_Characterization` replaces both with a structured group reusing the
`EquationConstant`/`CalibrationPoint` compound-dataset types already built for
`SynchronousSensor` — named (not positional) constants, plus room to actually
capture characterization points going forward.

*(Named `Power_Characterization` — renamed from an earlier "`Power_Calibration`"
draft, per the same rename applied to Change 4; see there for why the same
name is used in both places.)*

### Before / after

```
v1.0:
.../ClearBox/
    Volts_To_Watts_Algorithm   (e.g. "LINEAR")
    Volts_To_Watts_Params      (e.g. "50.5,107.5" — positional, algorithm-dependent)

v1.1:
Extensions/ClearBox/<train_id>/
    Power_Characterization/
        Algorithm_Type                        (e.g. "LINEAR")
        Algorithm_Equation                    (e.g. "W = a*V + b" — mechanically generated)
        Input_Type                            (e.g. "0-10 V")
        Units_Derived_Quantity                (e.g. "Watts")
        Derivation_Equation_Constants/        (compound dataset, EquationConstant rows: name+value)
        Characterization_Points/              (compound dataset, CalibrationPoint rows: input_value+output_value)
```

### StableModel

New struct — **shared with Change 4** (`LightSource.power_characterization`
uses the exact same struct; see there for why) — reusing existing
`EquationConstant`/`CalibrationPoint` types, nothing new to build for the
datasets themselves:

```
struct PowerCharacterization {
    algorithm_type: Option<String>,                      // was volts_to_watts_algorithm
    algorithm_equation: Option<String>,                   // new — mechanically generated or left blank, see below
    input_type: Option<String>,                           // new
    units_derived_quantity: Option<String>,                // new
    derivation_equation_constants: Vec<EquationConstant>,  // reused type
    characterization_points: Vec<CalibrationPoint>,        // reused type, field renamed to match the group
}
// ClearBox gains: power_characterization: Option<PowerCharacterization>
// ClearBox.volts_to_watts_algorithm / .volts_to_watts_params are unchanged,
// still populated for v1.0 files, simply None for v1.1 files.
```

### Derivation rules — confirmed

- **Coefficient convention (Equation Constants):** `Volts_To_Watts_Params` is always constant-term-first,
  ascending powers — `c0, c1, c2, …` for `W = c0 + c1·V + c2·V² + …`. `LINEAR` is just the
  2-term case with algorithm-specific names: `"50.5,107.5"` → `b=50.5` (c0), `a=107.5` (c1).
  `POLYNOMIAL`'s `"1,2,3"` → `1 + 2V + 3V²` uses the same ordering directly (`c0=1, c1=2, c2=3`).
  Rows are named to match `Algorithm_Equation`'s own variable names (`a`/`b` for `LINEAR`;
  `c0`/`c1`/`c2`/… for `POLYNOMIAL`) — same pattern `SynchronousSensor` already uses. Since
  `EquationConstant` rows are named (not positional), this removes exactly the ambiguity the
  old CSV string had.
- **Algorithm Equation:** mechanically generated from `Algorithm_Type` + constant
  count, not stored/derived per-record — `LINEAR` → `"W = a*V + b"` (fixed template);
  `POLYNOMIAL` → generated from however many constants exist (`"W = c0 + c1*V + c2*V^2 + ..."`).
- **Units Derived Quantity / Input Type — superseded (2026-09-01).** This manifest
  originally specified hardcoding these to `"Watts"` and `"0-10 V"` respectively for
  migrated records, on the reasoning that both are true by construction for a
  volts-to-watts conversion. Phase 2's writer-side fallback derivation (the
  `power_characterization.*` module in every language, which replaced the standalone
  migrate functions) instead leaves **both fields blank (`None`)** on every forward
  derivation, deliberately, even though `Units_Derived_Quantity` is technically knowable
  here: a hardcoded guess is a special case that would need re-litigating for every
  future version, and blank is honest about "not derivable from what's on disk" — see
  each language's `power_characterization.*` module docs. Confirmed empirically in the
  regenerated `fixtures/reference_config_v1_1_migrated.h5` (2026-09-01): both attrs are
  written empty, not `"Watts"`/`"0-10 V"`.
- **Characterization Points:** v1.0 never captured raw characterization measurements, so
  migrated data has nothing to populate this with — **zero rows for any v1.0→v1.1 migrated
  record.** Per explicit instruction: **the dataset itself must still be written (present,
  empty)**, not omitted — same "schema-complete over omitted" principle the mock manifest
  already uses for `Facility_ID`/`Config_Author` (attrs written even when `None`). This makes
  clear where the data belongs to anyone who later wants to populate it, rather than looking
  like the concept doesn't exist yet. Natively-authored v1.1 files (not migrated) can populate
  real rows once the capturing software starts recording them.
- **Unrecognized `Algorithm_Type` during migration:** only `LINEAR` and `POLYNOMIAL` are
  handled by the v1.0→v1.1 migration path — anything else is a **hard error**, consistent with
  the `Output_Path` conflict rule (Change 1): fail loud on an unrecognized value rather than
  guess or drop it silently. Matches reality today — every fixture in this repo uses `LINEAR`
  only; `POLYNOMIAL` is implemented but not exercised by any real fixture yet.
- **Error name/message — resolved (2026-08-31).** Same per-language approach as the
  Consolidate conflict rule (Change 1) — each language's own existing validation-error
  convention, no new shared exception type, standardized message content:
  `"Unrecognized Algorithm_Type '<value>' during v1.0→v1.1 migration (expected LINEAR or
  POLYNOMIAL)"`. Applies identically to Change 4's `Watts_To_Volts_Algorithm` check (same
  values, same rule, see there).
  - **Rust:** new `MachineConfigError::UnrecognizedAlgorithmType(String)` variant
    (`rust/src/error.rs`) — tuple-style, matching `UnsupportedVersion(String)`'s
    single-value shape.
  - **Python:** plain `raise ValueError(f"Unrecognized Algorithm_Type '{value}' "
    f"during v1.0→v1.1 migration (expected LINEAR or POLYNOMIAL)")` — no new
    exception class.
  - **Node.js:** plain `throw new Error(...)`, same message — no new error class.
  - **Go:** plain `fmt.Errorf("unrecognized Algorithm_Type %q during v1.0->v1.1 "+
    "migration (expected LINEAR or POLYNOMIAL)", value)` — no new error type.
  - **C++:** plain `throw std::runtime_error("Unrecognized Algorithm_Type '" +
    value + "' during v1.0->v1.1 migration (expected LINEAR or POLYNOMIAL)")` —
    no new exception class.

  **Superseded note (2026-09-01):** this hard error only ever applied to the standalone
  `migrate_v1_to_v1_1` functions Phase 2 removed — see [API impact](#api-impact). The
  writer-side fallback derivation that replaced them treats an unrecognized
  `Algorithm_Type` as best-effort *incompleteness*, not a hard error: it still derives
  positionally-named constants (`"0"`, `"1"`, …) rather than refusing to write. The
  Consolidate conflict rule above is unaffected — that stays a hard error on both paths.

### Backward migration (v1.1 → v1.0) — confirmed

Unlike forward migration, which must *interpret* an opaque, positional CSV string using
algorithm-specific knowledge (hence "unrecognized `Algorithm_Type`" is a real forward
failure mode), backward migration only *re-serializes* already-structured, already-named
data back into that CSV shape — it has no equivalent ambiguity to fail loudly on.

- **Volts_To_Watts_Algorithm** ← `Power_Characterization.algorithm_type`, direct copy.
- **Volts_To_Watts_Params** ← join `Derivation_Equation_Constants` row values with `,`,
  in ascending order per the same naming convention the forward rule established (`b`
  before `a` for the 2-term `LINEAR` case; `c0 < c1 < c2 < …` by numeric suffix for
  `POLYNOMIAL`). **Rows must be explicitly re-sorted by name before joining** — HDF5
  compound dataset rows are named, not positionally guaranteed, so on-disk order cannot
  be trusted even though the forward path always writes them in the correct order.
- **Missing data, confirmed:** if `Derivation_Equation_Constants` is empty (e.g. a
  natively-authored v1.1 record that only ever populated `Characterization_Points`),
  write `Volts_To_Watts_Params` as blank (`""`) rather than raising an error. This is
  **absence, not ambiguity** — unlike the Output_Path/Software_Trigger_Delay Consolidate
  conflict (Change 1) or forward migration's unrecognized-`Algorithm_Type` case, both of
  which involve genuine risk of misinterpreting or guessing at real, present-but-unclear
  data, there is nothing here to guess at — the data was simply never captured. Matches
  the schema's existing dominant convention (blank rather than error on absent optional
  data, e.g. `Facility_ID`/`Config_Author`).

### Algorithm_Type: enum vs. open string — resolved

**Resolved (2026-08-31): open string.** `Algorithm_Type` (as a StableModel concept, for
natively-authored v1.1 files — not migration) is not constrained to `Linear`/`Polynomial`
only; it stays an open string, so future algorithm types don't require a second
5-language regen cycle to add. The migration path itself is unaffected either way — it
only ever needs to handle `Linear`/`Polynomial` (v1.0 has never recorded anything else),
and anything else during migration is the hard error documented above.

## Change 4: `Watts_To_Volts_*` (Light_Source) replaced by `Power_Characterization/`

**Same shape as Change 3, applied to `Light_Source` instead of `ClearBox` — but
the data-availability is inverted**, so the derivation rules are not identical.
Reuses the `PowerCharacterization` struct from Change 3 (see StableModel there).

**Deliberately the same group name as Change 3** (`Power_Characterization`),
even though the two live at different HDF5 paths (`Extensions/ClearBox/<train_id>/`
vs. `.../Light_Source/`) and populate different StableModel fields — both
represent the identical concept (an algorithm + equation + constants +
characterization points describing a power conversion) applied to two
different devices. No path collision since the full paths differ; the shared
name reflects that they're the same *kind* of thing, not the same instance.

### Naming inconsistency in v1.0 — acknowledged, not addressed

The v1.0 attribute is named `Watts_To_Volts_Algorithm`/`Watts_To_Volts_Params`,
but the actual data represents the opposite direction: **input = Volts, output
= Watts.** Confirmed against `reference_config.h5`: `Watts_To_Volts_Params =
[1, 102.567, 3, 305.533, 6, 617.9, 9, 929.933, 10, 1028]` — the second value in
each pair (102.567 … 1028) lines up almost exactly with this same train's own
`Power_Max_Actual = 1033.0` / `Power_Min_Actual = 101.7`, confirming those are
watts, not volts. There is a v1.0-specific reason for the name that this
migration deliberately does not address — v1.1's `Algorithm_Type` and
`Units_Derived_Quantity` reflect the **true physical direction** (input
Volts → output Watts), not the legacy v1.0 attribute name. Flagged here so
nobody mistakes this for an oversight later.

### Derivation rules — confirmed

- **Characterization Points:** direct, unambiguous mechanical parse —
  `Watts_To_Volts_Params`'s alternating list becomes `CalibrationPoint{input_value,
  output_value}` rows pairwise, in order. No assumption needed, unlike Change 3's
  coefficient ordering.
- **Derivation Equation Constants:** the **inverse** situation from
  Change 3 — v1.0 never stored the fit *coefficients* for `Watts_To_Volts`, only
  raw characterization points, so migrated data has **zero rows** here. Same
  "present but empty, not omitted" rule as Change 3's `Characterization_Points`
  (schema-complete, makes clear where the data belongs).
- **Algorithm Equation — asymmetric with Change 3, confirmed:**
  - `LINEAR` → mechanically generated fixed 2-term template (`"W = a*V + b"`,
    same form as Change 3 — input Volts, output Watts, same direction).
  - `POLYNOMIAL` → **left blank (`None`) for migrated data, not generated,
    not an error.** Unlike Change 3, migrated data here never has fit
    coefficients to count, only characterization points — and point count does not
    reliably indicate polynomial degree, so there is no safe way to generate a
    correct equation string. **A human must add it later.** Confirmed
    intentional, not a gap to close.
- **Units Derived Quantity / Input Type — superseded (2026-09-01).** This manifest
  originally specified `"Watts"` (confirmed true here, verified directly against this
  train's own `Power_Max_Actual`/`Power_Min_Actual` matching the output values) and a
  hardcoded `"Volts"` placeholder, respectively. Same supersession as Change 3's
  identically-named bullet: Phase 2's writer-side fallback derivation leaves both
  blank (`None`) on every forward derivation instead, deliberately, for the same
  no-special-casing reasoning — see Change 3's superseded note. Confirmed empirically
  in the regenerated `fixtures/reference_config_v1_1_migrated.h5` (2026-09-01).
- **Unrecognized `Algorithm_Type` during migration:** same rule as Change 3 —
  only `LINEAR`/`POLYNOMIAL` are handled; anything else is a hard error, not a
  guess. Error name/message resolution is identical too — see Change 3's
  "Unrecognized `Algorithm_Type`" bullet for the per-language types and
  standardized message text; applies verbatim to `Watts_To_Volts_Algorithm`.
  Same [API impact](#api-impact) superseding note as Change 3: this hard error
  only applied to the removed migrate functions, not to the writer-side
  fallback derivation that replaced them.

### Backward migration (v1.1 → v1.0) — confirmed

Same reasoning as Change 3 — re-serialization, not interpretation, so there's no
unrecognized-type failure mode going backward.

- **Watts_To_Volts_Algorithm** ← `Power_Characterization.algorithm_type`, direct copy.
- **Watts_To_Volts_Params** ← flatten `Characterization_Points` rows pairwise
  (`input_value, output_value, input_value, output_value, …`) in **stored order** — no
  re-sorting needed here, unlike Change 3's named constants, since these rows were never
  named and their on-disk order is already the correct order to preserve.
- **Missing data, confirmed:** if `Characterization_Points` is empty (e.g. a
  natively-authored v1.1 record that only ever populated
  `Derivation_Equation_Constants`), write `Watts_To_Volts_Params` as blank (`""`) rather
  than raising an error — same absence-not-ambiguity reasoning as Change 3.

## API impact

The sections above describe the on-disk HDF5 layout and StableModel
differences between v1.0 and v1.1. Separately, `V1_1_IMPLEMENTATION_PLAN.md`'s
**Phase 2** ("writer-side fallback derivation, remove migrate functions")
changed the public writer API in every language, once all 5 languages'
`capabilities/v1_1/` adapters above existed. This section is the
consumer-facing summary of that change.

- **Readers are unaffected.** `MachineConfigReader` (and each language's
  reader adapter) reads whichever `File_Version` a file actually declares —
  no reader-side conversion between versions was ever added, and Phase 2
  didn't touch it.
- **Writers gained an optional target-version override**, letting a caller
  write an already-loaded config as a *different* `File_Version` than the one
  it was read as, without mutating the in-memory config just to express that
  intent:
  - **Python:** `MachineConfigWriter(config, target_version="1.1")`
  - **Rust:** `MachineConfigWriter::with_target_version(&config, "1.1")`
    (a second constructor, alongside the existing `MachineConfigWriter::new`)
  - **Node.js:** `new MachineConfigWriter(config, "1.1")`
  - **Go:** `machineconfig.NewWriter().WriteAs(config, path, "1.1")`
    (alongside the existing `.Write(config, path)`)
  - **C++:** `MachineConfigWriter(config, "1.1")` (a second constructor
    overload, alongside the existing single-argument one)

  In every language, the on-disk `File_Version` attribute always matches the
  resolved target version — never a mutation of the caller's own config
  object, only a corrected copy handed to the underlying adapter.
- **Each version's writer fills in whatever fields it has a native source
  for, and falls back to deriving them from the *other* version's on-disk
  shape only when its own native field is absent** (never the reverse, and
  never on the read path). This is what actually implements Changes 3–4
  above for a caller who never ran a migration step at all — e.g. writing a
  config that was only ever populated with v1.0's `Volts_To_Watts_*` fields
  out as a v1.1 file still produces a real `Power_Characterization/` group,
  derived on the fly. See `V1_1_IMPLEMENTATION_PLAN.md`'s Phase 2 write-up
  for the per-language derivation module (`power_characterization.*`) and
  its test coverage.
- **The standalone migrate functions this manifest originally specified —
  `migrate_v1_to_v1_1`/`migrate_v1_1_to_v1` and their per-language
  equivalents — were removed entirely.** The target-version override above
  replaces them: a caller that previously called a migrate function directly
  to convert a config, then wrote the result, should construct the writer
  with the desired `target_version` instead and write once. This also means
  the "unrecognized `Algorithm_Type`" hard error documented under Changes 3–4
  no longer applies on the writer path — see the superseded notes there.
